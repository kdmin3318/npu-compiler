## unfused + oneDNN 베이스라인 (변인 통제용)

목적: fusion 효과를 깨끗하게 분리해서 증명하려면, "같은 conv 연산 품질(oneDNN)
에서 fusion 여부만 다른" 비교가 필요함. `cpp_backend/inverted_residual_op_dnnl_unfused.cpp` -
naive 3중 for문 대신 oneDNN(`mingw-w64-ucrt-x86_64-onednn`, MSYS2 패키지)의
`convolution_forward` 프리미티브로 각 conv를 계산하되, 타일링(fusion)은
아직 적용 안 하고 각 단계(expand/depthwise/project) 결과를 기존과 동일하게
전체 크기 버퍼로 materialize.

**정확성 검증**: 5 seed, 기존과 동일한 방식으로 원본과 allclose 비교.

| seed | 최대 차이 | allclose |
|---|---|---|
| 0 | 3.58e-06 | True |
| 1 | 3.28e-06 | True |
| 2 | 2.98e-06 | True |
| 3 | 4.29e-06 | True |
| 4 | 4.05e-06 | True |

**전체: 모두 통과**

**성능 측정 (wall-clock, n=50)**:

| 구성 | 평균(ms) | 원본 대비 |
|---|---|---|
| 원본 (unfused, MLAS) | 2.1~4.1 | 1.00x |
| fused, naive C++ | 407~408 | ~100~190x |
| unfused, oneDNN | 66~75 | ~18~31x |

**구현 중 발견한 중요한 디테일**:
- oneDNN primitive(특히 JIT 커널) 생성 비용이 커서, conv 호출마다 매번
  새로 만들면 안 되고 "모양(shape)별로 1회 생성 후 재사용" 캐시가 필요함
  (`ConvShapeKey` 기반 캐시로 구현).
- `dnnl::algorithm::convolution_direct`로 강제 지정했을 때보다
  `convolution_auto`(oneDNN이 내부적으로 최적 구현을 선택, 1x1 conv는
  내부적으로 GEMM 경로를 탈 가능성)로 바꿨을 때 **약 3.7배** 빨라짐
  (unfused+oneDNN: naive 캐시 적용 후에도 ~280ms → auto 적용 후 ~70ms).

**해석**: naive 대비 oneDNN이 약 5~6배 빠르지만, 아직 fusion(타일링)이
전혀 적용 안 된 상태라 원본 MLAS 대비로는 여전히 18~31배 느림. 이는
예상된 결과 - SIMD/스레딩(oneDNN이 해결)과 메모리 트래픽(타일링이 해결)은
서로 다른 축이라, 이 숫자만으로는 fusion 효과를 아직 논할 수 없음.
다음 단계(fused+oneDNN, 타일링 적용)와 이 수치를 비교해야 fusion 자체의
순수 효과가 드러남.

### 추가 최적화 (버퍼 재사용 + 가중치 최적 레이아웃)

위 결과에서 MLAS 대비 격차가 꽤 커서(18~31배), fusion과 무관한 우리
하네스 자체의 비효율을 추가로 점검함:

1. **출력 버퍼 재사용**: 기존엔 conv 호출마다 `std::vector`를 매번 새로
   할당(`assign`)했음 - 원본 MLAS 경로는 ORT 메모리 플래너가 버퍼를
   1회만 할당해 재사용하는 것과 대조적. 커널 인스턴스(블록 하나)에
   귀속된 버퍼를 1회 할당 후 재사용하도록 변경.
2. **가중치 레이아웃을 oneDNN이 선택하게 함**: 기존엔 ONNX 원본 레이아웃
   (OIHW/GOIHW)을 강제 지정했는데, oneDNN은 보통 자체 선호 블록 레이아웃이
   있어서 이를 강제하면 성능이 덜 나옴. `format_tag::any`로 선언해 oneDNN이
   레이아웃을 고르게 하고, 가중치 값은 추론 내내 불변이므로 최적 레이아웃
   으로의 변환(reorder)을 커널 인스턴스당 1회만 수행 후 캐시.

   (주의: 이 reorder 결과 캐시는 전역이 아니라 커널 인스턴스별로 둬야 함 -
   MobileNetV2에는 shape은 같지만 가중치 값은 다른 반복 블록이 있어서,
   shape 기준 전역 캐시를 썼다면 다른 블록의 가중치를 잘못 재사용하는
   버그가 될 뻔함.)

**정확성**: 5 seed 재검증, 변화 없음(동일 오차, 모두 통과).

**성능 (wall-clock, n=50, 2회 측정)**:

| 구성 | 평균(ms) | 원본 대비 |
|---|---|---|
| 원본 (unfused, MLAS) | ~1.9~2.1 | 1.00x |
| fused, naive C++ | ~387~388 | ~187~201x |
| unfused, oneDNN (버퍼 재사용 + 최적 레이아웃) | **~51~57** | **~26~27x** |

1차(66~75ms, 18~31x)에서 추가로 약 20~25% 더 빨라짐. 여전히 MLAS 대비
20배 이상 느리지만 격차가 꾸준히 줄고 있음 - 남은 격차는 주로 MLAS의
MobileNet 특화 튜닝(특히 depthwise conv)과의 차이로 추정되며, fusion
(타일링) 전 단계에서 fair한 "같은 라이브러리" 베이스라인으로 쓰기에는
충분히 안정된 상태.

## 타일링 fusion 실험 결과 및 결론

### 1. 구현 버전과 정확성

| 구현 | 타일링 | 정확성 (5 seed, allclose) |
|---|---|---|
| unfused, oneDNN | 없음 | 통과 (오차 ~3e-6) |
| fused, oneDNN | 있음 (halo 타일) | 통과 (오차 ~3e-6) |
| fused, naive | 있음 (halo 타일) | 통과 (오차 ~3e-6~6e-6) |

정확성 검증 과정에서 **expand 이후 경계 0 패딩 누락 버그**를 찾아 수정했음. 원본은 depthwise가 expand 출력을 0으로 패딩하는데, 타일 구현은 block_input을 먼저 패딩한 뒤 expand를 돌려서 `expand(0) = bias ≠ 0`이 경계에 섞였음. expand 이후 진짜 이미지 경계 밖 위치를 다시 0으로 덮어쓰도록 수정. (Type A는 expand가 없어서 해당 없음.)

### 3. 오버헤드 원인 확인

타일 수가 늘수록 고정 비용이 누적됨. 타일 수 예: 이 블록(features.2, stride 2, T=12 기준) 5×5=25개 패치. oneDNN은 타일마다 primitive 실행과 스레드 동기화가 반복되고, naive는 타일마다 `ExtractPaddedTile`과 conv 출력 버퍼 초기화가 반복됨.

### 4. 캐시 크기와 버퍼 크기 (타겟 CPU 기준)

측정 대상: Intel Core Ultra 7 258V (Lunar Lake). 출처: notebookcheck.net 사양 정리.
- L1: P코어당 192KB
- L2: P코어당 2.5MB (E코어는 4MB 클러스터 공유)
- L3: 12MB (전체 공유)

가장 큰 중간 버퍼는 features.2의 expand 출력 `96×112×112×4B ≈ 4.8MB`. L2보다 크고 L3 안에는 들어감. 즉 **타일링 없는 unfused에서도 대부분의 중간 결과가 DRAM까지 가지 않고 L3에서 처리됨.** 타일링으로 줄일 DRAM 트래픽이 원래 작았음.

### 5. 패치 크기 계산 버그 (수정 완료)

> 수정 완료: 두 타일링 구현(`dnnl_fused`, `naive_tiled`) 모두 P를 먼저 계산하도록
> 바꿨고, budget은 환경변수 `INVRES_BUDGET_BYTES`로 받음(기본 2.5MB). 수정 후
> 기본값과 256KB에서 정확성 재검증 통과(5 seed). 아래 2번 스윕 표는 **수정 전**
> 측정값임.

초기 구현은 캐시 예산 식(`sqrt(budget/(4C)) - 2`)으로 **출력 타일 T를 먼저 정하고**, 패치 크기는 나중에 stride를 반영해 역산했음. 이 순서가 틀렸음. 올바른 순서:
1. 패치 크기 P를 캐시 예산에서 직접 계산: `C_expand × P × P × 4 ≤ budget` → 256KB, C=96이면 P≈26
2. P에서 출력 T를 역산: `T = (P-3)/stride + 1` → stride 2면 T=12

초기 구현에서 stride 2 블록(features.2)은 T=24, 패치 49가 되어 expand 버퍼가 `96×49×49×4 ≈ 900KB`, 목표의 약 3.5배였음. 즉 캐시 예산을 실제로 지키지 못하고 있었음.

이 버그를 고치면 패치가 작아지고 타일 수가 늘어나서(features.2 기준 9개 → 25개), 오버헤드가 더 커짐. 따라서 버그 수정이 wall-clock 개선으로 이어지지는 않음.

**영향 범위 (caveat)**: 이 CPU에서는 expand 버퍼 약 900KB가 L2(2.5MB) 안에 들어가므로 용량 초과로 인한 성능 손실은 없었음. 다만 설계 목표(256KB 예산)는 stride 2 블록에서 지켜지지 않았음. 그래서 스윕 표의 budget 라벨은 stride 2 블록에 대해 실제 버퍼 크기와 일치하지 않으며, 수정 후 재측정이 필요함. 작은 온칩 메모리(256KB~1MB) 타깃에서는 이 버그가 결과를 직접 바꿀 수 있음.

### 6. 패딩과 halo에 대한 정리

- 원본 depthwise는 pad=1. 타일 구현은 conv 호출에 pad=0을 넘기되, 패딩은 `ExtractPaddedTile`이 **진짜 이미지 경계에서만** 0으로 채워서 처리함. 그래서 내부 타일 경계를 가짜 경계로 만들지 않음.
- 패치 크기 26(캐시 기준)과 T=12를 만드는 데 필요한 최소 크기 25의 차이로, 패치 1칸이 해당 타일 계산에서 쓰이지 않음. 이 칸은 옆 타일이 halo로 다시 가져가서 사용하므로 정보 손실은 없고, 연산 중복만 약간 늘어남. 정확도에는 영향 없음(검증 완료).
- halo 겹침은 정확도를 위해 필수. 겹치지 않게 떼면 경계 출력이 원본과 달라짐.

### 7. 측정 환경 제약

- VTune `memory-access` 분석은 하드웨어 이벤트 샘플링이 필요한데, Windows의 VBS/Hyper-V가 켜져 있어서(`HyperVisorPresent: True`) 실행이 막힘. 설치된 VTune 2026.4의 `hotspots` 소프트웨어 샘플링은 동작함.
- 따라서 **DRAM 트래픽과 캐시 미스를 실측으로 확인하지 못함.** 측정한 것은 wall-clock 시간뿐이며, 이는 메모리 효과 외에 구현 오버헤드를 함께 포함함.
- VBS를 끄고 재부팅하면 VTune 메모리 분석이 가능해짐(보안 기능 약화 있음).

### 8. MLAS 관련 확인

- `onnxruntime.dll`의 외부 노출 함수는 2개뿐(`OrtGetApiBase`, `OrtSessionOptionsAppendExecutionProvider_CPU`). MLAS 함수는 노출되지 않아 외부에서 직접 호출 불가.
- 성능 격차 분해(wall-clock 기준): naive(~400ms) → oneDNN(~46ms)은 약 9배로 SIMD·스레딩·알고리즘 선택 효과. oneDNN → MLAS(~2ms)는 약 20배인데, 원인은 측정하지 않음(MLAS의 depthwise 튜닝 등으로 추정).
- MLAS가 빠른 이유: 주된 요인은 연산 최적화이고, 중간 결과가 L3 안에 있어 메모리 병목이 작았던 것은 부차적 요인.

### 9. 결론

- **가설(fusion이 메모리 트래픽을 줄여 latency를 개선한다)은 이 실험으로 반증되지 않았음. 다만 이 환경에서는 검증할 수 없었음.**
  - 측정 환경: L3 12MB가 중간 버퍼를 흡수해 DRAM 트래픽이 원래 작음. VTune 메모리 분석 불가(VBS). wall-clock은 구현 오버헤드가 지배함.
- 효과가 나타나려면 중간 버퍼가 캐시를 넘고 DRAM 왕복이 실제로 일어나는 환경이 필요함(예: NPU, MCU처럼 on-chip 메모리가 작은 타깃). 이는 MCUNetV2 및 DATE 2019 논문의 결과와 방향이 일치함.
- 이 CPU에서 wall-clock 기준으로 MLAS를 이기는 것은 현재 구현 방식으로는 달성하지 못함.

| 1 | L2 2.5MB | 1.20 | 1.28 | −6.7% (−2.1, −10.6, +3.4) |
| 1 | L3 12MB | 1.08 | 1.40 | −30.2% (−30.2, −29.7, −20.9) |
| 1 | untiled (대조군) | 1.08 | 1.08 | +0.2% (+0.2, −10.0, +5.4) |

해석: 기본 스레드의 L3 12MB 행은 기준을 통과하지만, 타일링이 없는 대조군도 비슷하게 개선(+27.9%, 편차 큼)됐고
1스레드에서는 같은 조건이 30% 악화됨. 따라서 타일링에 의한 메모리 효과가 아니라 멀티스레드 스케줄링 차이로 판단.
**L3를 넘기는 입력에서도 타일링 fusion 효과는 관측되지 않음.**

이득 상한 추정: fusion이 없애는 중간 텐서 트래픽은 224 기준 약 92MB(`estimate.py`, 과대 추정치). 실효 대역폭
약 100GB/s를 가정하면 약 0.9ms로, oneDNN 실행 시간(약 50ms)의 약 2%. 448에서는 트래픽과 연산이 함께 4배가 되어
비율이 거의 같음. 즉 이 구성에서는 fusion으로 얻을 수 있는 최대 이득이 타일링 오버헤드와 측정 노이즈보다 작음.
